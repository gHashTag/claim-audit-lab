# Золотое сито

Инструмент, чтобы разбирать численные математические утверждения быстро и
одинаково. Утверждение описывается один раз как данные, дальше его прогоняет
фиксированный каскад сит. Каждое сито — независимая причина НЕ поверить.

Язык всех ответов и артефактов — только русский. Код, комментарии и
идентификаторы могут быть английскими.

## Когда применять

- Просят проверить численное утверждение, константу, порог, p-значение, колонку
  «expected / reference / theoretical».
- Просят разобрать статистику расстояний между нулями дзета-функции против GUE,
  константу Хинчина, любую подобную величину.
- Идёт тик непрерывного цикла аудита корпуса Trinity: ручные разборы запрещены,
  утверждение оформляется как задача сита.
- Просят объяснить, почему вердикт ПУСТО или ВОПРОС, а не находка.
- Просят добавить проверку эталонов в CI.

## Главное правило

Ручной одноразовый скрипт под каждое утверждение больше не пишется. Скрипт
допустим только как `reference`, `observed` или `null_model` внутри `Claim`.
Вердикт берётся из сита, а не из собственного впечатления.

## Как пользоваться

Каталог `scripts/` этого скила — работающий пакет. Скопируй его в рабочую
папку (например `/home/user/workspace/goldsieve`) и запускай оттуда:

    python3 -m goldsieve.selftest              самопроверка: 234 пройдено, 0 провалено
    GOLDSIEVE_FULL=1 python3 -m goldsieve.selftest   с тяжёлыми эталонами: 141
    python3 -m goldsieve run cases/задача.py   прогнать задачу
    python3 -m goldsieve run cases/*.py --json out.json
    python3 -m goldsieve power cases/задача.py минимально различимое отклонение
    python3 -m goldsieve cover <корень> --registry claims.yaml   покрытие (ТРИАЖ)
    python3 -m goldsieve new cases/задача.py   заготовка новой задачи
    python3 -m goldsieve regress --registry claims.yaml   ОБЯЗАТЕЛЬНО в начале тика

**Первым делом всегда самопроверка.** Если она падает — вся работа тика уходит
на ремонт сита и ни на что больше. Код возврата `run` ненулевой при вердиктах
ОПРОВЕРГНУТО или ПУСТО, поэтому сито можно ставить в CI.

## Двадцать одно сито: девятнадцать сит и два мета-сита

| сито | что ловит |
|---|---|
| С1 регенерируемость | эталон процитирован, а не вычислим — сравнивать не с чем |
| С2 заявленное=эталон | заявленное число против пересчитанного |
| С3 данные=эталон | измерение из данных против пересчитанного |
| С4 подставка ловится | проверка, которая прошла бы и на неверном ответе |
| С5 контроль | негативный: шум не должен давать эталон; позитивный: генерическая модель обязана его дать |
| С6 сходимость | результат зависит от сетки или разрешения |
| С7 выбор оценки | вывод меняет знак при законной смене оценки |
| С8 бюджет точности | заявленный эффект меньше погрешности входа |
| С9 конечный размер | расхождение объясняется конечностью выборки |
| С10 неопределённость | расхождение внутри выборочного шума: масштаб — полуширина бутстрэп-интервала с поправкой Шидака, терпимость ВЫВОДИТСЯ |
| С11 слишком хорошо | согласие точнее шума сразу по нескольким статистикам — признак числа, списанного из теории |
| С12 независимый метод | эталон не подтверждён вторым, принципиально иным путём; порог берётся из измеренного разброса второго метода |
| С15 внешняя цель | предсказательное утверждение, сверенное с числом из того же документа: тавтология, прошла бы при любом значении формулы. Отклонение меряется в сигмах погрешности ВНЕШНЕГО измерения, порог 3 сигма |
| С16 подгонка под ответ | попадание, ожидаемое по случаю при переборе формул (look-elsewhere на пространстве формул): VOID если ожидаемых попаданий >= 1 или случайная цель накрывается в >= 50 % случаев |
| С17 описание короче данных | формула не сжимает данные по MDL Риссанена: биты совпадения <= биты описания -> ВОПРОС |
| С19 достаточность арифметики | вердикт может быть артефактом округления: то же вычисление на 50 знаках против double, требуется запас в 100 раз против погрешности, относительно которой считается вердикт. FAIL -> ВОПРОС, проверяется РАНЬШЕ опровержений |
| С20 эффективное число попыток | порог по Шидаку выведен при ПРЕДПОЛОЖЕНИИ независимости перебранных формул, а члены семейства лежат на логарифмической решётке. Сито не подменяет порог «правильным», а проверяет УСТОЙЧИВОСТЬ вывода к законной замене M на M_eff (Li & Ji 2005 + trials factor Гросса-Витальса). FAIL -> ВОПРОС |
| С21 алгебраическая объяснимость | PSLQ находит соотношение при малых коэффициентах -> цель воспроизводится семейством, совпадение бесплатно, VOID. Плюс граница бейкеровского типа (усиление Матвеева 2000) как теоретический потолок близости. При наличии log pi граница НЕПРИМЕНИМА и сито обязано дать OPEN с этой причиной |
| С18 объявленная область | фактический перебор шире объявленного -> ОПРОВЕРГНУТО (занижен размер перебора, значит занижена и поправка на множественность) |
| С13 объявленные пропуски | молчаливый skip: каждый пропуск обязан иметь причину под точным номером сита |
| С14 сквозная подставка | подделка прогоняется через ВЕСЬ каскад; если получает ПОДТВЕРЖДЕНО — конвейер вырожден |

Сита С15 и С16 требуют поля `search_size` (размер фактического перебора). Без
него порог остаётся 3 сигма, но помечается словом СОГЛАШЕНИЕ — принимать такой
порог за выведенный нельзя.

С13 и С14 — мета-сита: они проверяют не утверждение, а сам прогон.

## Вердикты

- **ПОДТВЕРЖДЕНО** — все применимые сита прошли.
- **ОПРОВЕРГНУТО** — расхождение с вычисляемым эталоном при живых контролях.
- **ВОПРОС** — не хватает рецепта, либо вывод зависит от оценки, сетки, размера
  выборки. Это НЕ находка и не подаётся как находка.
- **ПУСТО** — проверка вырождена: она прошла бы и на неверном ответе.

Своды С15 и С18: FAIL по ним даёт ОПРОВЕРГНУТО (при С10 PASS — ВОПРОС), FAIL по
С17 даёт ВОПРОС, VOID по С15 или С16 даёт ПУСТО.

Порядок правил в своде не переставляется: вырожденная проверка бьёт всё,
отсутствие вычисляемого эталона бьёт любое расхождение. Расхождение по С2/С3
становится ОПРОВЕРГНУТО только если С10 признал его значимым — иначе ВОПРОС:
расхождения могло и не быть. Провал С11 или С12 тоже даёт ВОПРОС. Утверждение без
пересчитываемого эталона не может стать находкой — правило вшито в код.

## Как оформить новую задачу

`python3 -m goldsieve new cases/тема.py`, затем заполнить поля `Claim`:

- `stated` — что заявлено (число или dict именованных чисел).
- `reference` — **вычисляемый** эталон из определений. Не литерал из документа.
- `observed` — измерение из данных репозитория.
- `wrong` — заведомо неверный ответ той же формы, поставленный там, где он
  реально отличается от верного, а не в точке пересечения кривых. Можно СПИСОК
  подставок: одна вручную придуманная проверяет меньше набора.
- `null_model` + `null_kind`: `negative` — шум не должен давать эталон;
  `positive` — генерическая по построению модель обязана его дать.
- необязательные: `estimators` (разные законные оценки), `bins` (корзины по
  размеру/высоте, x → 0 в пределе бесконечных данных), `resolutions` + `resolve`
  (сходимость по сетке), `precision` (погрешность входа), `tolerance`.

- `sample` + `statistics` — сырые наблюдения и словарь «имя → f(массив)». Без
  них С10 и С11 не работают, а значит расхождение нельзя назвать значимым.
- `reference_alt` + `alt_tolerance` — второй метод и его ВЫВОДИМАЯ погрешность
  (например разброс по сидам Монте-Карло), а не назначенный порог.
- `inputs` — файлы данных: попадут в провенанс с sha256 и коммитом корпуса.
- `skip_reasons` — словарь «номер сита → причина». Незаявленный пропуск даёт
  ВОПРОС: контроль не имеет права слабеть молча.

Всё незаполненное пропускается со статусом skip — но пропуск обязан быть
объявлен.

## Провенанс и отпечаток рецепта

Каждый отчёт содержит sha256 входных файлов, коммит корпуса, версии
Python/numpy/scipy, α, терпимость и **отпечаток рецепта** — sha256 исходного
текста функций эталона, подставки, наблюдения и контроля. Если терпимость или
подставку подкрутили после того, как результат стал известен, отпечаток
изменится. Это машинный аналог пре-регистрации.

## Задачи в комплекте

- `scripts/cases/zeta_gue.py` — расстояния между нулями дзета-функции против
  **точного** закона зазоров GUE: `E₂(s) = det(I − K_s)` с синус-ядром, метод
  Нюстрёма (`scripts/goldsieve/refs/gue_exact_gap.py`), а не surmise Вигнера.
  Surmise сам отклоняется от точного закона на 0.3–0.5%, поэтому для разговора
  об эффектах порядка 2% как эталон не годится — и сито С4 это показывает.
- `scripts/cases/sacred_fit_multiplicity.py` — содержательны ли совпадения
  «священных формул»: разбор 90 строк таблиц, 32 нарушения объявленных границ
  (фактический перебор 123 201 против объявленных 20 412), поправка на
  множественность, MDL-проверка (-4,76 бит, сжатия нет).
- `scripts/cases/sacred_external_targets.py` — те же формулы против ВНЕШНИХ
  измерений: tau_n = 878,4 +- 0,5 с (PDG 2024), m_p/m_e = 1836,152673426(32)
  (CODATA 2022), T_c = 156,5 +- 1,5 МэВ (HotQCD 2019), m_X17 = 16,66 +- 0,59 МэВ
  (VNU; MEG II сигнала НЕ нашла). Образец того, как оформлять `external_target`.
- `scripts/cases/sacred_random_probability.py` — оценка значимости корпуса
  «1 из 500 (0,2 %) против 1 из 35 (2,9 %), около 10 сигма». Проверяется именно
  вероятность, потому что значимость выводится из неё. Эталон 0,998: при переборе
  123 201 формулы почти каждая цель обязана попасть в класс «точнее 0,01 %»
  случайно, поэтому класс EXACT не достижение, а недонаполнение (32 из ожидаемых
  67). Образец того, как строить позитивный контроль: он обязан воспроизводить
  ЭТАЛОН другим путём, а не заявленное значение — на этом я ошибся дважды подряд,
  и оба раза сорвало сито С5.
- `scripts/cases/khinchin.py` — константа Хинчина у частных цепной дроби;
  эталон считается по произведению Хинчина, подставка — золотое сечение (все
  частные равны единице), позитивный контроль — равномерные вещественные.

## Тавтологические проверки: главный урок версии 3

Тик крона выдал восемь вердиктов ПОДТВЕРЖДЕНО на утверждениях вида «формула
2*3^4*pi^4*phi^-6 даёт 879,4 с». Это провал ПРОВЕРКИ, не корпуса: и левая, и
правая часть взяты из одного выражения, поэтому такая сверка прошла бы при любом
значении формулы. Разрешающая способность теста равна нулю.

Правило: любое утверждение вида «формула даёт физическую величину» оформляется с
`claim_kind="prediction"` и ОБЯЗАТЕЛЬНЫМ `external_target` — измерением из
первоисточника (CODATA, PDG, журнальная статья) с погрешностью и URL. Без него
сито С15 даёт ПУСТО, и это правильный вердикт.

Отклонение считается в СИГМАХ погрешности измерения, а не в процентах. Пример,
почему это важно: «ошибка 0,109 %» для m_p/m_e звучит приемлемо, но CODATA знает
это отношение с относительной погрешностью 1,7e-11, и в единицах этой
погрешности промах составляет 6,3e7 сигм.

## Паспорт рецепта zeta и происхождение 0,4009 (тик 59)

Рецепт развёртки зафиксирован машинно и больше не собирается заново: нули —
`data/zeta/zeros_odlyzko_100k.txt` (sha16 `3436c916a7878261`, 100 000 нулей,
γ 14,134725142…74920,827498994, 99 999 зазоров, коммит корпуса `04430c0`);
θ(t) = Im logΓ(1/4 + i t/2) − (t/2)·ln π; точная развёртка
s_i = (θ(γ_{i+1}) − θ(γ_i))/π; развёртка корпуса — ведущий член
(γ_{i+1} − γ_i)·ln(γ_i/2π)/(2π) с множителем по НИЖНЕМУ нулю; края НЕ
исключаются; std выборочная, ddof=1; перцентили — линейная интерполяция.
Контроли паспорта: θ восстанавливает номер нуля N = 99 999,405 против 100 000;
среднее развёрнутых зазоров 1,000000 (θ) и 0,999986 (ведущий член).

`0,42201569295012265 = sqrt(3π/8 − 1)` — это std **surmise Вигнера**, и она
воспроизведена четырьмя независимыми путями: замкнутая форма
(0,4220156929501229), mpmath 50 знаков по плотности, Гаусс–Лежандр по функции
ВЫЖИВАНИЯ E[s²] = ∫2s(1−F)ds (иной объект, Δ = 1,09e-11) и Монте-Карло 4·10⁶ по
обратной CDF, seed 20260815 (|Δ| = 9,9e-6 при 4·SE = 5,97e-4). Точный закон
зазоров GUE даёт 0,424258, то есть колонка корпуса «GUE (computed)» отличается
от точного закона на +0,531 %.

**Корпусное 0,4009 — настоящее измерение, а не артефакт рецепта.** Пятнадцать
законных вариантов (ddof=0/1, ренормировка на среднее, множитель по
нижнему/верхнему/среднему нулю, точная θ-развёртка, обрезание 1/10/100/1000
зазоров с краёв, объединённая внутрикорзинная std по 10 корзинам, среднее
корзинных std) дают 0,400924…0,401127, то есть +0,006 %…+0,057 % относительно
напечатанного; одиннадцать воспроизводят его в пределах 5e-5. Версии «иная
нормировка», «иная выборка», «ошибка корпуса» этим ОТВЕРГНУТЫ. Напечатанное
корпусом отклонение −5,00 % посчитано относительно surmise; относительно
точного закона GUE то же измерение даёт −5,50 %, то есть выбранный корпусом
эталон занижает собственное отклонение корпуса. Кейс
`cases/zeta_unfolding_std_recipe_20260815.py`, вердикт ПОДТВЕРЖДЕНО на
CPython 3.14.3, отпечаток рецепта `ca42e009adaca3bf`, паспорт цели
`9e1b6776d16762e6`.

Три пути в одном кейсе разводятся не словами, а стеком: эталон — scipy
`loggamma` + numpy; наблюдение — чистый Python со своим парсером файла и
`math.fsum`; второй эталон — mpmath на 30 знаках с накоплением моментов в
Python. Это и есть рабочая форма запрета тавтологий для измеряемых статистик.

## Терпимость из печатной точности, а не из головы

Если заявленное число напечатано с k знаками после запятой, допуск сравнения
ВЫВОДИТСЯ: половина последнего разряда, делённая на само значение
(для 0,4009 это 5e-5/0,4009 = 1,247e-4 относительных). Назначать «5e-5
относительных» нельзя: это жёстче, чем разрешает публикация, и даёт FAIL по С2
там, где корпус не мог напечатать точнее. Сито С3 поднимает порог до печатной
точности само, С2 — нет, поэтому пару С2/С3 надо согласовывать вручную.

## Бюджет информационной новизны — решение о запуске, НЕ вердикт

Повторяющиеся классы (округление, отношение двух напечатанных чисел,
элементарное p-value) берутся только если цель покрывает новый класс рецепта,
новый источник, новую категорию ошибки или новый риск для публичного
утверждения. Пример работы бюджета: цель «колонка 0,4220 подписана как GUE,
хотя это surmise» в тике 59 НЕ бралась, потому что класс уже закрыт
зарегистрированным «surmise Вигнера годится как эталон на уровне 2 % →
ОПРОВЕРГНУТО». Отказ бюджета пишется в ведомость как решение о выборе цели, а
вердикт при этом не выносится вообще.

Ловушка тика 59: при ОДНОЙ статистике С11 уходит в skip, и без явной причины
под ключом «С11» мета-сито С13 честно даёт FAIL, а весь кейс — ВОПРОС.
Объявлять пропуски надо для ВСЕХ номеров из `sieve_numbers()`, включая те, что
пропускаются «очевидно».

## Порог разрешающей способности: как НЕ надо и как надо

**Отменённая формула (версия 3, ошибка).** Я выводил порог как
eps* = ln10 * D / (2M), где D — размах декад. Самопроверка версии 4 это
опровергла: D выбирает человек, и для одних и тех же целей защитимы D=5
(порог 4,7e-5) и D=30 (порог 2,8e-4) — разница в шесть раз. По такой формуле
получается любой удобный вывод. **Не предъявлять её как результат.** Число
8,1e-5 из версии 3 привязано к произвольному D=5.

**Замена без свободного параметра (версия 4).** Плотность семейства считается
локально, вокруг самой цели: rho(V) — число членов на декаду вблизи V. Тогда

    eps_loc(V) = ln10 / (2 * rho(V))

Выбирать нечего. Ширина окна усреднения остаётся, но плотность локально гладкая:
втрое разное окно меняет порог на 1 %. Прямой счёт попаданий не годится —
из-за совпадающих значений в семействе счёт скачет целыми числами 0 -> 3, поэтому
именно плотность. Модуль `scripts/goldsieve/threshold.py`, самопроверка 9 проверок,
включая проверку, которая падает, если зависимость старой формулы от D исчезнет
(защита от «починки» подбором D).

Для семейства n*3^k*pi^m*phi^p*e^q корпуса Trinity локальный порог по целям
лежит в 6,6e-5...1,0e-4. Из 32 строк класса EXACT шесть грубее даже его, то есть
бесплатны безусловно.

## Порог значимости выводится, а не назначается

Привычные 3 сигма — дисциплинарная привычка. Порог сита С15 выводится по
поправке Шидака из размера перебора: alpha_loc = 1 - (1 - alpha)^(1/M), порог —
обратная функция хвоста нормального распределения от alpha_loc/2.

| перебор M | alpha_loc | порог |
|---|---|---|
| 1 | 0,05 | 1,96 сигма |
| 100 | 5,1e-4 | 3,47 сигма |
| 20 412 (объявлено корпусом) | 2,5e-6 | 4,71 сигма |
| 123 201 (фактически) | 4,2e-7 | 5,06 сигма |

Привычные 3 сигма соответствуют перебору порядка 20 формул. Ужесточение до 5,06
НЕ перевернуло ни одного прежнего вердикта — это существеннее, чем если бы
перевернуло: значит порог не подгонялся под желаемый результат.

Оговорка, которую надо держать открытой: Шидак предполагает независимость
перебираемых формул, а члены семейства зависимы (общие множители), поэтому
реальный порог, вероятно, чуть ниже 5,06 сигма. Величина зависимости не оценена.

## Точность арифметики: доказывать, а не заменять

Соблазн «заменить float на mpmath везде» ничего не доказывает: у mpmath точность
тоже конечна. Правильно — измерить и сравнить с тем, что требуется. Сито С19
считает то же выражение на 50 знаках и требует запас 100x.

| величина | значение |
|---|---|
| ошибка double на типичном члене семейства | 2,5e-16 |
| худшая по выборке с углами диапазона | 8,4e-16 при (6,-5,-3,5,-4) |
| допустимый предел при погрешности CODATA 1,7e-11 | 1,7e-13 |

Запас три порядка: double здесь достаточна, и это ДОКАЗАНО числом. Опровержение
по m_p/m_e артефактом округления не является. Модуль `scripts/goldsieve/exact.py`.

## Команда power: чему верить, а чему нет

Луп 6 обнаружил, что 28 записей «минимально различимое отклонение 0,10 %» в
ведомости были НЕДЕЙСТВИТЕЛЬНЫ. Причина: мутант объявлял пропуски только для сит
С1..С14, поэтому С15..С19 оставались необъявленными, С13 честно давал FAIL, и
мутант получал ВОПРОС при ЛЮБОМ сдвиге — включая нулевой. Печаталась первая точка
сетки, то есть свойство сетки, а не проверки.

Правила, которые теперь вшиты:

- Номера сит для объявления пропусков берутся из `sieve_numbers()` — они
  собираются с пустого прогона. НЕ использовать `len(ALL_SIEVES)`: нумерация не
  плотная (С13 и С14 — мета-сита), и счётчик длины даёт 17 при максимальном
  номере 19. Самопроверка падает, если вернуть счётчик.
- Перед сканированием обязательна КАЛИБРОВКА нулевым сдвигом. Не совпал вердикт
  с базовым — число не печатается вообще, печатается причина. Молчаливое число
  хуже отсутствия числа.
- Мощность определена только для ПОДТВЕРЖДЁННОГО утверждения: мутация заменяет
  заявленное значение эталоном, поэтому у опровергнутого расхождение исчезает по
  построению. Отсекать ДО калибровки, иначе калибровка предъявит претензию не по
  адресу.
- При нулевом допуске сканирование не проводится: разрешение задаётся
  арифметикой (2,2e-16 относительных), и это сообщается словами.
- Сетка идёт от 1e-9; срыв на первой точке печатается с предупреждением, что
  истинное разрешение может быть лучше.

## Однородность пары «заявленное — эталон»

Луп 7: проверка сравнивала заявленные 0,2 % (колонка СТАНДАРТНОГО перебора) с
эталоном, посчитанным для РАСШИРЕННОГО перебора. Знак расхождения был верен,
но множитель «в 500 раз» — нет: пара неоднородна. Корректно 321x для
стандартного (0,002 против 0,642) и 34x для расширенного (0,029 против 0,998).

Правило: если корпус даёт величину в нескольких вариантах — колонки, режимы,
версии — каждая проверяется против эталона СВОЕГО варианта. Однородность пары
проверяется явно, а не предполагается. При сомнении оформляй отдельный Claim на
каждый вариант: так расхождение получает осмысленную величину, а не только знак.

Там же найдено новое опровержение: объявленный размер стандартного перебора
20 412 против 54 756 комбинаций, которые дают объявленные там же границы.
Размер перебора нельзя брать из текста — он считается из границ, потому что от
него зависит поправка на множественность.

## Приоритет цели: не давать циклу вырождаться

Четыре тика подряд выдали ПОДТВЕРЖДЕНО на печатных значениях вида
phi^phi = 2,17846. Это дефект ИНСТРУМЕНТА, не лени: `cover` сортировал файлы по
ЧИСЛУ констант, а таблиц значений в корпусе больше всего, поэтому дешёвый класс
систематически выносился наверх. Сортировка по количеству — свойство корпуса, а
не ценности.

`goldsieve.coverage.priority(line)` возвращает:

- **2** — за числом стоит внешнее измерение или погрешность (measured, PDG,
  CODATA, ±, sigma, p-value, значимость). Только здесь возможны ОПРОВЕРГНУТО и
  ПУСТО.
- **1** — статистическое или выборочное заявление (вероятность, ожидание,
  распределение, число комбинаций, порог).
- **0** — печатное значение замкнутого выражения. Проверяет округление
  калькулятора, а не утверждение.

Порядок проверок важен: внешнее измерение бьёт шаблон печатного значения, потому
что строка `z_re = 7.670 ± 0.73` подходит под оба. Приоритет 0 брать в тик
только когда целей 2 и 1 не осталось.

## Класс дефектов «ложное значение = отсутствие значения»

Три дефекта подряд оказались одним и тем же: С10 падало на пустой таблице
статистик (луп 5), С15 возвращало OPEN при ТОЧНОМ совпадении с внешней целью,
потому что `if not nums.get(...)` трактовало валидный нулевой промах как
отсутствие сравнения (тик крона), диапазон пропусков не покрывал новые номера сит
(луп 6). Во всех случаях валидное «пустое» значение — ноль, пустой словарь,
непокрытый номер — принималось за «сравнения не было».

Правило: проверять наличие КЛЮЧА, а не истинность значения (`in`, а не `if not
...get()`). И: общий перехват исключений внутри сита маскирует дефект инструмента
под обвинение утверждению — каждый новый режим отказа обязан получать свой явный
статус.

## Свод: когда С10 смягчает опровержение

PASS у С10 понижает опровержение до ВОПРОСА только если С10 сопоставил хотя бы
одну статистику с ЗАЯВЛЕННОЙ величиной. Иначе опровержение можно было бы тихо
погасить, подложив безобидную выборку по другой величине. Признак выставляется
внутри С10 полем `сопоставлено_с_заявленным`.

Второе правило (луп 10). Если С10 объявил `significance_untestable` — выборка
детерминированная, разброс равен нулю, — то расхождение по **С3** понижается до
ВОПРОСА, а расхождение по **С2, С15 или С18 — НЕТ**.

Границу пришлось искать через ошибку. Первая версия правила понижала любое
расхождение по С2/С3, и обязательный перепрогон реестра сразу перевернул пять
арифметических опровержений вида «в каталоге написано 182,8 против
пересчитанного значения» в ВОПРОС. Там нет и не может быть выборочного шума:
сравниваются два вычислимых числа. Выборочная значимость относится ТОЛЬКО к
величине, измеренной из данных.

## Подтип причины вердикта и предписанное действие (луп 10)

Отчёт несёт три машиночитаемых поля помимо вердикта: `reason_code` (подтип
причины), `action` (что делать) и `aggregatable` (можно ли складывать в счётчик
находок). Смысл: девять вердиктов ПУСТО по разным причинам требуют разных
действий, а в виде одного слова «ПУСТО» они выглядят одинаково.

Подтипы: `resolution_limited`, `multiplicity_limited`, `model_nonidentifiable`,
`systematics_unmodeled`, `significance_untestable`, `out_of_sample`,
`no_computable_reference`, `estimator_dependent`, `arithmetic_insufficient`,
`algebraically_explainable`, `observation_mismatch`, `external_mismatch`,
`domain_understated`, `too_good`, `no_second_method`, `no_compression`,
`meff_unstable`, `pipeline_broken`, `control_broken`,
`input_precision_limited`, `confirmed`, `unclassified`.

Два последних введены после того, как ПУСТО дважды означало дефект МОЕЙ
проверки, а не утверждения: `control_broken` — сломан позитивный контроль;
`input_precision_limited` — заявленный эффект не превышает погрешность входа.
Оба входят в `NON_AGGREGATABLE`: вердикт, полученный при неисправной проверке,
в счётчик находок не идёт.

Порядок правил в `reason_of` не переставляется: множественность и
алгебраическая объяснимость сильнее обоих новых подтипов — иначе совпадение,
купленное перебором, объяснялось бы «сломанным контролем» и уходило из-под
требования предрегистрации пространства поиска.

## Зависимость данных: блочный бутстрэп (луп 10)

Обычный бутстрэп предполагает независимость наблюдений. На зависимой выборке он
занижает разброс, то есть ЗАВЫШАЕТ значимость расхождения — ровно та ошибка,
против которой стоит С10.

Поле задачи `bootstrap_block`: `None` (независимые), `"auto"` (длина блока
выводится из автокорреляции по правилу Соколя, 2·τ), целое (задана вручную).
Реализация — скользящие блоки (Kunsch 1989) в `stats.py`.

Измерено в самопроверке модуля: на AR(1) с ρ = 0,8 блочный интервал шире
независимого (12,15 против 4,23), на белом шуме НЕ раздувается (это подставка:
метод, раздувающий все интервалы подряд, бесполезен), длина блока 18 против 2.
Для развёрнутых зазоров дзеты длина блока = 1: на первом лаге антикорреляция.

## Гейт полезности: две вырожденные оси (луп 10)

Гейт встроен в отчёт триажа (`coverage.gate_report`), бюджет собирается ИЗ
ВЕРДИКТОВ РЕЕСТРА (`budget_from_registry`), а не хранится отдельно — иначе его
можно рассинхронизировать с ведомостью.

Первая версия интеграции допускала **828 целей из 828** и при этом печатала
отпечаток настроек, придавая себе вид работающей проверки. Два дефекта:

1. Ключ новизны включал имя файла — каждый файл был новым классом, бюджет
   невозможно исчерпать. Класс сведён к приоритету цели: `corpus:p0/p1/p2`.
2. Ось `precision` получала «ожидаемый эффект» = приоритет триажа при
   разрешении 1, то есть информативность измерялась самой сортировкой. Ось
   объявлена НЕобъявленной, как и `discrimination` (различающие модели известны
   только после написания кейса — объявлять их за автора самообман).

После ремонта: 827 допусков, 1 отказ на корпусе Trinity. Правило для будущих
тиков: **по триажным целям гейт почти неинформативен**, его сила — на внешних
предсказательных целях, где эффект, разрешение и модели объявлены. Отказ гейта
(`SKIPPED_LOW_INFORMATION`) — решение о запуске, НЕ вердикт по утверждению.

## Печатная точность заявленного числа (луп 10)

`printed_tolerance()` в `sieve.py`: порог сравнения в С3 не может быть строже
половины последнего значащего разряда заявленного числа. Прежде задача с
терпимостью 1e-12 против выписанного из корпуса «0,91» давала FAIL всегда —
опровергалось округление, а не утверждение.

## Автоматический пропуск сита (луп 10)

`Result.auto_skip` + `Result.reason_code`: пропуск, объявленный САМИМ ситом,
несёт машинную причину и не считается молчаливым — С13 его принимает.
Требовать от автора задачи объяснять честный отказ инструмента значило бы
наказывать за прозрачность.

Первый случай применения: С10 на детерминированной выборке. Прежде выдавался
`z = +∞` и FAIL, то есть инструмент обвинял утверждение в СВОЕЙ неспособности
измерить разброс.

## Ловушка автоматизации: крон не должен восстанавливать код (луп 10)

Тик 36 фонового крона выполнял в тексте задачи шаг «восстановить goldsieve из
репозитория» и переписал ядро версией v8 поверх свежей рабочей копии, стерев
правки четырёх файлов. Уцелели только те файлы, которых в v8 не было.

Правило: **в тексте recurring-задачи не должно быть безусловного восстановления
кода**. Допустимо только: прогнать самопроверку и, если она падает, ОСТАНОВИТЬСЯ
и сообщить — а не «починить» откатом. Рабочая копия в песочнице всегда новее
репозитория.

## Перепрогон реестра (regress)

    python3 -m goldsieve regress --registry claims.yaml [--update]

Обязательный шаг в НАЧАЛЕ каждого тика. Усиление каскада может молча перевернуть
прежние вердикты, и тогда ведомость начинает противоречить инструменту. В версии
3 перепрогон перевернул 7 вердиктов ПОДТВЕРЖДЕНО -> ВОПРОС/ПУСТО — то есть
прежние «подтверждения» были тавтологиями. В версии 4 он поймал 4 молчаливых
переворота ПОДТВЕРЖДЕНО -> ВОПРОС, вызванных МОЕЙ ЖЕ правкой: ключи
`skip_reasons` были записаны полным именем сита («С19 достаточность арифметики»),
а С13 сверяет только номер (`s.split()[0]`). Ключ обязан быть ровно «С19».

Ловушка, на которой я попался: массовая автоправка case-файлов сломала
`cases/zeta_gue.py` синтаксически (вставка попала внутрь dict-comprehension).
После любой массовой правки — прогонять `regress`, а не только импорт нового
кода. Сопоставление имён в реестре устойчиво к регистру и лишним пробелам.

## Ошибка самого инструмента как находка

Если по ходу работы окажется, что сито дало неправильный вердикт — это находка
об инструменте, а не о корпусе. Починить сито, добавить случай в
`goldsieve/selftest.py`, работу засчитать. Так уже было: сито С5 считало любое
совпадение контроля с эталоном признаком вырождения, а в задаче Хинчина
равномерные вещественные по теореме обязаны давать K. Отсюда появилось деление
контроля на негативный и позитивный.

Так было и в третий раз: сито С10 падало с ValueError на пустой таблице, если ни
одно имя статистики не совпало с ключами эталона. Падение перехватывалось общим
обработчиком и превращалось в FAIL — то есть ошибка инструмента предъявлялась
утверждению как его вина. Урок общий: общий перехват исключений внутри сита
маскирует дефект инструмента под обвинение утверждению; каждый новый режим отказа
обязан получать свой явный статус.

Так было и во второй раз: независимый эталон GUE по спектрам случайных матриц
делил расстояния на полукруговую плотность и промахнулся на −25% по всем
статистикам, потому что нормировка ансамбля не совпадала с радиусом 2. Ошибку
поймала самопроверка модуля, а не рассуждение. Лечение: развёртка делением на
среднее по короткому окну — тогда второй метод не наследует ни одной константы
из первого. Отсюда правило: **у каждого модуля-эталона своя самопроверка с
подставкой**, иначе «независимый метод» независим только на словах.

## Три оси не сливаются в одно число (луп 9)

Отклонение в сигмах, поправка на множественность и длина описания — ТРИ
раздельные координаты вердикта. Свести их в один скаляр без произвольного
параметра нельзя: «автоматический» байесовский Occam-фактор имеет контрпримеры
(Belot), множественность входит только через приор (Scott & Berger 2010),
многокритериальный выбор без назначенных весов даёт лишь множество Парето, а
шкала байес-фактора — конвенция (Kass & Raftery). Попытка ввести единый скаляр
повторила бы ошибку версии 3 с произвольным размахом декад D.

Правило: вердикт остаётся точкой в трёх координатах, а порядок приоритетов между
осями фиксируется в рецепте и попадает в отпечаток — то есть объявляется ДО того,
как результат известен. Объединение осей — решение о приоритетах, а не
вычисление, и подавать его как вычисление запрещено.

## Однородность пары распространяется и на множественность

Правило лупа 7 («каждая величина проверяется против эталона СВОЕГО варианта»)

семейства обязан быть ОДИН.

## Инженерный контур тика (BINDING, директива 2026-08-14)

Свобода творчества не требуется — требуется воспроизводимый контур. Каждый тик
проходит пять фаз, и у каждой фазы обязательный выход. Фаза без своего выхода
считается невыполненной.

| фаза | обязательный выход |
|---|---|
| контракт | цель, входы, ожидаемый артефакт, критерии приёмки, бюджет времени и вызовов |
| разведка | факты, источники, риски, ограничения |
| планирование | шаги, критерии готовности, точки ручного контроля |
| исполнение | версионированные изменения и машиночитаемый результат |
| верификация | самопроверка, регресс реестра, сравнение с baseline |
| доклад | что сделано, что ДОКАЗАНО, что НЕ доказано, следующий ход |

Правила, вытекающие из директивы:

- **Детерминированное не поручать модели.** Парсинг, арифметика, сравнение с
  порогом, классификация причины, сборка таблиц — только код. Роль модели —
  постановка утверждения и разбор аномалии, не счёт.
- **Один вызов — одна операция.** Кейс проверяет одно утверждение; сито отвечает
  за одну причину недоверия.
- **Approval gate на всё необратимое.** push, merge, PR, публикация, удаление,
  расходы, отправка сообщений — только после явного «да» пользователя.
- **Не сделал — не докладывай; не проверил — не считай сделанным; не можешь
  доказать — помечай гипотезой.** В отчёте раздел «что НЕ доказано» обязателен.
- **Работа через ветку и PR, не в main.** Ветка `audit/<тема>-<дата>` или
  `tools/goldsieve-*`, понятный diff, тесты, план отката.
- **Неуверенность объявляется.** Перечислить недостающие факты и перейти в
  режим только чтения, а не достраивать догадкой.
- **Журнал тика** в ведомости: вход, план, вызовы, вердикты, отпечатки,
  ссылка на коммит.

## Урок тика 37: ПОДТВЕРЖДЕНО на сравнении величины с собой (луп 11)

Фоновый тик 37 выдал **ПОДТВЕРЖДЕНО** для сводки `χ²/dof = 2,67 ± 0,49` по
десяти высотным корзинам. Разбор показал два вырождения в самом кейсе:

1. `observed` возвращал `reference()` — таблица сравнивалась сама с собой, и
   С3 давал PASS при любом содержании таблицы.
2. `reference_alt` повторял ту же арифметику через `Decimal` — «независимый
   метод» С12 был тем же путём в другом числовом типе, расхождение ровно 0.

Оба PASS складывались в ПОДТВЕРЖДЕНО. Добавлен машинный признак: **все
отклонения РОВНО нулевые = вырождение**. Измерение, полученное иным путём, не
совпадает с эталоном бит в бит — остаётся хотя бы округление порядка машинного
эпсилон. Ровный ноль означает сравнение величины с собой.

- С3 при тождестве → VOID, подтип `observation_is_reference`, действие
  «переписать наблюдение так, чтобы оно получалось иным путём».
- С12 при тождестве → VOID, подтип `no_second_method`.
- Оба подтипа в `NON_AGGREGATABLE`: это состояние проверки, не утверждения.

После ремонта вердикт того же кейса: **ПУСТО / observation_is_reference**.
Отдельно: сама величина `χ²/dof = 2,67` означает ПЛОХОЕ согласие с моделью
(хорошее согласие ≈ 1), поэтому слово ПОДТВЕРЖДЕНО в этой строке читалось бы
как одобрение утверждения, которого нет. Проверялась бухгалтерия сводки, не
физика.

Правило на будущее: в кейсе `observed` обязан получаться ИНЫМ путём, чем
`reference` (другой парсер, другой файл, другая формула), а `reference_alt` —
принципиально иным методом, а не переписанной арифметикой.

**Признак вырождения берётся ИЗ КОДА, не из значений.** Первая версия ремонта
объявляла вырождением ровное нулевое расхождение — и перепрогон реестра
немедленно перевернул 17 корректных вердиктов: у целых величин (20 412
комбинаций) и простых констант (3^φ, ln 3) независимый путь высокой точности
ЗАКОННО совпадает с эталоном до последнего бита. Детектор `_is_same_computation`
считает вырождением только тождество объектов или тело из единственного
`return _reference()`.

**Вырождение С3/С12 не гасит опровержение по внешней цели.** Второй дефект того
же лупа: правило «любой VOID → ПУСТО» понижало опровержение формулы m_p/m_e с
промахом 6,3e7 сигм, потому что в том же кейсе observed вызывал reference.
Вырождение С3 или С12 означает лишь, что сравнение ВНУТРИ корпуса ничего не
даёт; FAIL по С15 (внешняя цель) или С18 (объявленная область) опирается на
погрешность внешнего измерения или прямой подсчёт и остаётся в силе. Вырождение
по С16 продолжает гасить вывод — оно относится к сути.

Общий урок лупа: **усиление сита проверяется перепрогоном реестра, а не
собственным впечатлением.** Оба ремонта этого лупа были неверны в первой
версии, и оба раза ошибку нашёл перепрогон, а не рассуждение.

Побочно исправлена собственная фикстура самопроверки «слишком точное согласие»:
её наблюдение тоже было тождественно эталону и после ремонта давало ПУСТО
вместо ВОПРОСА. Отличие сдвинуто на 1e-9 — проверяется С11, а не тождество.

## Косвенная тавтология и калибровка (луп 12)

Прямую тавтологию `def _observed(): return _reference()` закрыл луп 11. Луп 12
закрыл её через посредника: `_observed -> _table -> _panel -> _reference`.
Модуль `goldsieve/identity.py` строит по AST замыкание «прозрачных обёрток»
эталона до неподвижной точки.

**Критерий — не достижимость эталона, а отсутствие своего источника данных.**
Функция признаётся обёрткой, только если у неё нет параметров, в теле есть
вызов эталона или уже признанной обёртки, и НЕТ ни одного другого источника
значений (вызова вне узкого белого списка чистых операций, чтения файла,
обращения к вводу-выводу). Поэтому законны и не помечаются: наблюдение,
читающее корпус само; общий парсер у наблюдения и эталона (общий предок есть,
но эталон из наблюдения не достижим); наблюдение с входным параметром.

Проверка калибруется, а не объявляется работающей:
`python3 calibrate_identity.py` строит разметку НЕЗАВИСИМЫМ текстовым разбором
кейсов и сверяет с детектором. Луп 12: 46 кейсов, размечено 3, помечено 3,
ложных срабатываний 0, пропусков 0; специфичность 1,0000 [43/43]. Честная
оговорка: 43 кейса — мало, правило трёх даёт верхнюю оценку ложных ~7 %.

### Тихий отказ — худший вид дефекта проверки

Первая версия детектора определяла модуль через `inspect.getmodule()`. CLI
загружает кейсы через `importlib.util.module_from_spec` БЕЗ регистрации в
`sys.modules`, поэтому `getmodule()` возвращал None и весь разбор графа молча не
выполнялся ни на одном реальном прогоне. Проверка «работает» и при этом не
проверяет ничего. Файл берётся из `fn.__code__.co_filename`. Guard обязателен и
прогоняет НАСТОЯЩУЮ загрузку вне `sys.modules`, вместе с подставкой «честный
кейс в тех же условиях не помечается».

Правило: у каждой новой проверки обязателен guard на условия РЕАЛЬНОГО вызова,
а не только на подготовленные в памяти объекты.

### Ручная разметка сама является источником ошибки

Разметка «единственный вырожденный кейс — тик 37» была неверна в обе стороны:
пропустила два кейса с `observed=<то же имя, что reference>` и назвала настоящее
вырождение ложным срабатыванием. Затем ошибся и машинный разметчик: жадный
regex тел функций съедал пустые строки перед следующим `def` и терял функцию —
калибровка показывала ложную цифру. Вывод: метрику качества проверки тоже надо
проверять, и разметка обязана строиться машинно и независимо.

## Молчание детектора — не покрытие (тик 40, луп 13)

Три вердикта ПОДТВЕРЖДЕНО на кейсах с `globals`, `functools.partial` и `lambda`
были прочитаны как «класс конструкций закрыт». Измерение это опровергло:
детектор на этих формах молчал, потому что разбирал по `__name__`, которого у
lambda, partial и вызываемого объекта нет. Чувствительность на корпусе фикстур
была **0,1852 [5/27]** при нуле ложных срабатываний.

**Правило**: у любой проверки должна быть ИЗМЕРЕННАЯ чувствительность на
корпусе подтверждённых положительных примеров. Отсутствие срабатываний само по
себе не отличает исправную проверку от неработающей — это тот же тихий отказ,
что был найден в лупе 12, просто в другом месте.

### Обязательный минимум для новой проверки

1. **Корпус фикстур** (`goldsieve/identity_corpus.py`): положительные примеры
   по классам конструкций + негативные стресс-ловушки (эквивалентный код с
   разным AST, альфа-переименование, перестановка независимых операций, равные
   захваченные значения при разных идентификаторах объектов, сериализация).
   Фикстуры грузятся `module_from_spec` БЕЗ регистрации в `sys.modules` — только
   так воспроизводятся условия реального вызова из CLI.
2. **Измерение** (`measure_identity.py`): таблица «класс -> поймано/пропущено»,
   чувствительность и специфичность, ненулевой код возврата при пропуске.
3. **Мутационная проверка** (`mutation_identity.py`): в проверку ВНОСЯТСЯ
   поломки, и корпус обязан поймать каждую. Мутант получается дописыванием
   переопределения к тексту модуля или заменой одной строки; грузится и
   подставляется в `sys.modules` — рабочий файл не правится. Мутационная
   проверка тика 40 нашла дефект самого корпуса: поломка чтения захваченной
   ячейки не давала ни одного пропуска, то есть путь не проверялся по существу.
4. **Матрица интерпретаторов**: не менее двух версий CPython. Пропуск
   интерпретатора без зависимостей ОБЪЯВЛЯЕТСЯ с причиной, а не выбрасывается
   молча — иначе матрица перестаёт что-либо проверять.

### Baseline и reason-code

`baseline.py snapshot | check | show`. Baseline фиксирует sha256 каждого файла
инструмента, отпечаток набора файлов, версии интерпретатора и пакетов, платформу,
seed, HEAD корпуса, метрики (получаются ПРОГОНОМ, не переписыванием чисел) и все
вердикты реестра в JSON и CSV с отпечатком. Метрика без привязки к состоянию
инструмента ничего не значит.

`baseline/reasons.yaml`: КАЖДОЕ отклонение от baseline обязано иметь
reason-code, иначе гейт закрывается. Коды: `corpus-fixed`,
`corpus-data-changed`, `sieve-strengthened`, `sieve-defect`,
`wrapper-identity-change`, `claim-restated`. Неклассифицированное отклонение —
это будущее «молчаливое исключение», то есть потерянный дефект.

### Гейт обязан быть проверен подставкой

`ci_gate.sh` блокирует слияние при пропуске вырождения, ложном срабатывании,
необнаруженной поломке, ухудшении метрики или неклассифицированном отклонении.
Сам гейт проверяется двумя подставками: поломка в рабочем файле должна дать
«метрика ухудшилась», а подмена вердикта в baseline без записи в `reasons.yaml` —
«вердикт изменился без reason-code». Непроверенный гейт прошёл бы и на сломанном
инструменте.

### Что остаётся недоказанным даже при 28/28 и 16/16

Ноль ложных на 60 наблюдениях даёт по правилу трёх верхнюю оценку доли ложных
около 5 % при 95 % доверии, а не ноль. Не покрыты дескрипторы, `property`,
`__getattr__`, метаклассы, `exec`/`eval`, `lru_cache`, генераторы, корутины,
C-расширения, `contextvars`. Калибровка построена только для детектора
тождественности: ложные срабатывания остальных сит остаются OPEN.

## Тик 41: заморозка, три уровня статуса, манифест, pre-filter

Пять уроков, каждый — от подставки, а не от впечатления.

**1. Отпечаток обязан охватывать сам гейт.** До тика 41 baseline охватывал
`goldsieve/`, `cases/` и пять файлов в корне, но НЕ `ci_gate.sh`. Значит, шаг
можно было удалить из гейта, и ни один охваченный файл не изменился бы. Правило:
всё, что решает, открыт гейт или закрыт (сам гейт, манифест покрытия, счётчики),
входит в отпечаток. Проверка: удаление строки `step ...` обязано менять
отпечаток файлов.

**2. Заморозка версии.** `baseline.py freeze` пишет `baseline/frozen-v12.json`
плюс отдельный sha256 ТЕЛА записи. `frozen` печатает дельту и падает только при
нарушении целостности записи, `refreeze` требует `--i-have-review`. Смысл: чтобы
метрики прошлой квалификации нельзя было переписать задним числом. Проверяется
двумя подставками — повторный freeze обязан отказать, правка тела без пересчёта
обязана дать «ЦЕЛОСТНОСТЬ ЗАМОРОЗКИ НАРУШЕНА».

**3. Три уровня статуса вместо двух.** `goldsieve/scope.py`:
`verified-in-scope` (только с указанием класса конструкций И версии рантайма
вида `3.14.3`), `not-evaluated` (обязательна причина), `unsupported`
(обязательна причина). `lint_text()` ищет «подтвержден» и требует в той же
строке версию рантайма и класс конструкций. Линтер проверен на историческом
тексте тика 39 — он его ловит.

Ограничение линтера объявлено: он проверяет СОСЕДСТВО, а не смысл, и даёт
ложное срабатывание на метатексте (когда слово цитируется как предмет
проверки). Это НЕ чинится белым списком: выключатель «слово в кавычках не
считать» дал бы готовый способ обойти линтер.

**4. Coverage manifest — объявление, сверяемое кодом.** По каждому конструкту:
поддержан/нет, число позитивных и негативных фикстур, мутационные цели,
fallback, известные ограничения. `coverage_manifest.py` сверяет каждое число с
`identity_corpus.classes()` и `mutation_identity.MUTANTS`; расхождение закрывает
гейт. На первом же прогоне манифест опроверг МОИ ЖЕ объявленные числа негативных
фикстур — они были выдуманы. Манифест без сверки кодом бесполезен: он
превратился бы в то же заявление о покрытии, которого нет.

Отдельное правило из манифеста: **поддержанный класс без мутационной цели —
непроверенное молчание.** Прохождение фикстур доказывает возврат True, но не то,
что он получен именно этим разбором.

**5. Одноточечная мутация может не различать при избыточном покрытии.**
Отключение `calls` в `_value_sources` детектор пережил: имя вызываемой функции
попадает и в `calls` (узел `ast.Call`), и в `names` (узел `ast.Name` в позиции
`func`). Вывод не «мутация плохая», а «класс покрыт двумя независимыми путями» —
и это измеренное свойство. Мутация обязана убирать все пути покрытия класса,
иначе она не различает наличие разбора от отсутствия.

**6. Pre-filter: дешёвая оценка до дорогого сита.** `goldsieve/prefilter.py`
решает RUN / SKIP-VOID по трём критериям: локальный порог разрешающей
способности семейства, относительная погрешность цели, ожидаемое число
случайных попаданий. Асимметрия сознательная: при любой неопределённости входа —
RUN, потому что пропустить годную цель дороже, чем потратить сито.

Проверка предсказательной силы делается на целях с УЖЕ известными вердиктами
каскада, а не на новых: 5 согласий из 5 (tau_n, T_c, X17, z_re → SKIP-VOID при
вердикте ПУСТО; m_p/m_e → RUN при вердикте ОПРОВЕРГНУТО).

**Как это получилось — важнее результата.** Первая сверка дала 4 из 5, и
расхождение оказалось МОЕЙ ошибкой: передан размер расширенного перебора
(123 201) при стандартных диапазонах (20 412) — буквальный повтор урока лупа 7.
Поэтому в pre-filter встроен ОТКАЗ: `search_size != declared_size(ranges)` даёт
«ПАРА НЕОДНОРОДНА» и решение RUN. Расхождение исчезло как следствие починки, а
не подгонки порога. Границы семейства НЕ угадываются: канонический
`ACTUAL_RANGES` живёт в `threshold.py` и даёт ровно 123 201; мои угаданные
границы давали 84 942.

**7. Технические счётчики при молчаливом abort.** Правило «сорванный тик не
пишет вердиктов» остаётся, но отсутствие записи и работающая инфраструктура на
письме выглядят одинаково. `tick_counters.py` считает СОБЫТИЯ ИНФРАСТРУКТУРЫ
(`tick_started`, `tick_completed`, `tick_aborted_timeout`, `tick_aborted_other`,
`gate_closed`, `verdict_flips`, `manifest_mismatch`, `frozen_integrity_fail`) —
без вердиктов, атомарной записью, с устойчивостью к битому файлу.

`MIN_OBSERVED = 10`: ниже этого числа наблюдений вердикт о здоровье НЕ
выносится. Причина — та же, что сорвала команду `power` в лупе 6: при одном
наблюдении доля равна 0 или 1, и любой вывод был бы свойством размера выборки.
Порог доли срывов 0,34 помечен словом СОГЛАШЕНИЕ: выводить его неоткуда.

**Формулировка о платформах.** Пока в матрице только Linux-песочница, писать
«платформонезависимо» нельзя. Действующая формулировка — «проверено на
указанных версиях CPython»; macOS и Windows держатся в статусе `not-evaluated`
с причиной. `pc bash` на локальном устройстве не ответил в трёх попытках
(120 с, 120 с, 630 с) — брутфорс запрещён, статус не меняется.

**Состав гейта после тика 41.** На всей матрице интерпретаторов: корпус
фикстур, мутационная проверка, трёхуровневые статусы, счётчики тика; при наличии
numpy/pyyaml — самопроверка каскада и калибровка. Один раз: гейт baseline,

## Наблюдаемость оболочки: run_id, замок, статусы (тик 43)

Оболочка тика 42 экономила набор команд, но не оставляла следа: по отчёту
нельзя было сказать, каким вызовом получен артефакт и завершился ли он вообще.

| команда | что делает |
|---|---|
| `tri runs [N]` | последние вызовы: run_id, статус, код возврата, артефакты |
| `tri verify` | перепроверка снимка по SHA-256 без сети |
| `tri archive` | контракт архива скила: записи, порядок, детерминизм |
| `tri bench [N]` | измерение времени команд: median, p95, min/max, cold/warm |

**Журнал вызовов** (`goldsieve/runlog.py`, самопроверка 19): каждый вызов
оставляет событие `start` и событие `finish` в JSONL — run_id, номер тика,
коммит корпуса, отпечаток baseline, команда, PID, время, код возврата и
ссылки на артефакты. Словарь статусов ЗАКРЫТ: `running`, `passed`, `failed`,
`aborted`, `pending`, `not-evaluated`. Коды 124/130/137/143 дают `aborted`, а
не `failed`: срыв инфраструктуры и найденная ошибка требуют разных действий, и
смешивать их нельзя.

Три дефекта, найденных самопроверками этого же тика:

- **обрыв записи губит СЛЕДУЮЩУЮ запись, а не свою.** Процесс, убитый на
  середине строки, оставляет хвост без перевода строки; следующая запись
  приклеивается к нему, и теряются ОБЕ. Закрыто чтением последнего байта перед
  дописыванием и признаком `after_truncated_write` в событии.
- **замок брался дважды одним процессом.** Проверка «жив ли владелец»
  принимала собственный PID за признак брошенного замка. Закрыто набором
  удержаний внутри процесса.
- **cold нельзя считать первой из двадцати точек.** Тогда тёплых остаётся
  девятнадцать, а p95 требует двадцати — и молча не печатается. Cold измеряется
  отдельной точкой.

**Замок.** Исключительные команды (`gate`, `quick`, `snapshot`, `skill`,
`archive`, `bench`) берут файловый замок. Второй такой вызов получает код 3 и
внятное сообщение, а не ждёт: два тика, пишущих в один baseline и одну
ведомость, — это порча состояния, а не очередь. Замок мёртвого владельца
подбирается.

**Проверяемый снимок** (`snapshot_manifest.py`, самопроверка 8): sha256 и
размер по трём группам — файлы инструмента (состав берётся из
`baseline._tool_files()`, один источник правды), документы (отчёты, ведомость,
`claims.yaml`, манифест покрытия, очередь задач) и журналы. `verify` доказывает
отсутствие сети, а не декларирует его: на время проверки `socket.socket`
подменяется классом, который выбрасывает исключение при любой попытке.

**Контракт архива** (`archive_contract.py`, самопроверка 9). Предел скила в 100
считается по ЗАПИСЯМ архива, и записи каталогов тоже считаются — в тике 42 это
стоило отказа сервиса. Теперь правило проверяется кодом вместе с порядком,
отсутствием дубликатов и детерминизмом: две сборки из одного состояния обязаны
дать одинаковый SHA-256. Для этого архив собирается Python-кодом с
фиксированным временем записи (1980-01-01) и фиксированными правами; обычный
`zip` кладёт время изменения файла и детерминизма не даёт.

**Интеграционные тесты оболочки** (`tri_integration_test.py`, 14 утверждений).
Самопроверка внутри `tri` зовёт функции напрямую и не видит оболочки вовсе.
Здесь запускается настоящий исполняемый файл со своей средой (`GOLDSIEVE_RUNS`,
`GOLDSIEVE_COUNTERS`, `TRI_LEDGER`, `TRI_LOCK`): фон, одновременный `watch`,
столкновение замков, убийство владельца сигналом, падение команды, обрыв
журнала, повторный запуск, `tick abort`. Отдельное утверждение проверяет, что
тест не оставил следов в НАСТОЯЩЕЙ ведомости — иначе тест сам портил бы то, что
проверяет.

**Что доказано измерением, а что нет.** Оболочка не ускоряет работу: под ней те
же процессы. Измеренный накладной расход — около +0,1 с на вызов (двадцать
тёплых повторов). Экономия тика была в числе команд и в отсутствии ошибок
набора; это величина не секундная, и как ускорение тика она остаётся гипотезой.
Среднее не публикуется — одна задержка планировщика сдвигает его сильнее, чем
весь эффект.

## Журнал под цепочкой хешей и checkpoint (тик 44)

Журнал вызовов (`GOLDSIEVE_RUNS`, по умолчанию `runs.jsonl` в каталоге крона)
теперь append-only цепочка: у записи есть `seq`, `prev_hash`, `entry_hash`,
`run_id`, `timestamp`, хеш считается по каноническому JSON БЕЗ поля собственного
хеша. `./tri log verify` печатает машинный JSON
(`ok/lines/chained/pre_chain/head/violations/guarantee/not_guaranteed`) и даёт
код 1 при нарушении. Самопроверка `python3 -m goldsieve.chain` — 29 проверок,
среди них шесть подстановок: правка поля, удаление середины, перестановка двух
событий, подмена `prev_hash`, повреждение последней строки, новый сегмент без
ссылки на checkpoint.

`./tri snapshot` дополнительно пишет `baseline/log-checkpoint.json`
(`log_name`, `last_seq`, `head_hash`, `snapshot_sha256`), и `snapshot_manifest.py
verify` сверяет живой журнал с этим checkpoint.

**Растущий файл нельзя фиксировать целиком.** Первая версия писала в снимок
sha256 всего журнала — расхождение появлялось после ЛЮБОГО вызова, то есть шум
вместо проверки. Правильно — префиксная сверка (`chain.prefix_digest` /
`chain.check_prefix`): рост разрешён, правка старой записи ловится, укорачивание
ловится.

**Цепочка — НЕ подпись.** Она не доказывает авторства и не мешает переписать
журнал вместе с checkpoint. Ограничение зафиксировано машинно: поле
`limitations` в снимке (4 пункта) и `limits` у `goldsieve/chain.py` в
`coverage_manifest.yaml`, плюс две самопроверки следят за их наличием. Писать
«журнал защищён от подделки» запрещено; корректно — «незаметная правка задним
числом обнаруживается».

**Дефект, который надо помнить: путь журнала не прописывать жёстко.** Проверка
снимка искала журнал по фиксированному пути, поэтому при другом
`GOLDSIEVE_RUNS` (так работает измеритель стоимости) снимок покрывал журнал,
который ничто не пишет, и молчал о реально пишущемся. Гейт ВНУТРИ измерения
давал `failed`, и только это вскрыло дефект. Путь берётся из
`runlog.runs_path()`.

**Дефект мета-проверки мутации.** `python3 -m goldsieve.chain` создаёт модуль
`__main__`, а `import goldsieve.chain` — второй объект того же файла: мутация
правила одну копию, проверялась другая. Лечится `_self = sys.modules[__name__]`.

**Стоимость журналирования (`chain_overhead.py`, самопроверка 8).** Точка «до»
делается переключателем `GOLDSIEVE_CHAIN=0` и ОБЯЗАТЕЛЬНО в отдельный журнал
(`GOLDSIEVE_RUNS=/tmp/...`), иначе pre-chain запись после цепочечной = нарушение
`pre-chain-entry-after-chained` и гейт закроется. Замок разводится через
`TRI_LOCK`. Публикуются median/p95/min/max и сырые точки, среднее НЕ
публикуется; p95 только при n ≥ 20, иначе печатается причина. Вердикт выносится
КОДОМ: разность медиан меньше разброса повторов → «замедление НЕ измерено».
Измерение тика 44: quick n=20 median 9,563 → 9,575 (+0,012 при разбросе 0,360),
p95 9,8322 → 9,7418; gate n=3 median 52,015 → 52,168 (+0,153 при разбросе
0,780). Отсюда нельзя сказать «расходов нет» — только «они меньше шума
измерения».

**Фон в песочнице.** `sleep N; tail файл` в одном вызове может быть прерван по
таймауту инструмента и утащить фоновую задачу; надёжная форма —
`setsid nohup bash -c '...' >лог 2>&1 </dev/null & disown`, затем отдельные
короткие опросы. Пустой лог при живом процессе — не признак сбоя: смотреть
`ps` и растущий журнал вызовов.

## Правила честности (BINDING)

- Триаж не выдавать за аудит: непроверенное — «вопрос», не «находка».
- Эталон обязан быть вычисляемым, а не процитированным.
- У каждого инструмента обязана быть самопроверка, включая guard на
  подставленный неверный ответ, стоящий там, где неверный ответ отличается.

## Тик 48: вердикт не бывает безусловным

Обнаруженный дефект класса: каскад умел проверять тождества, но не умел
отличать «формула вычислена верно» от «формула применима». Порог Шидака
выведён ПРИ НЕЗАВИСИМОСТИ испытаний, а члены семейства зависимы
(общие множители). Вердикт ПОДТВЕРЖДЕНО на таком утверждении читался
как разрешение пользоваться порогом, чего не было доказано.

**Модуль `goldsieve/preconditions.py`** (самопроверка 20, в том числе 6
подставок). Поле паспорта цели `tests_independent`:

| объявлено | статус охвата | вердикт |
|---|---|---|
| `true` | verified-in-scope | высший вердикт остаётся |
| `unknown` | assumption-unverified | ДОПУЩЕНИЕ НЕ ПРОВЕРЕНО |
| не объявлено при признаках множественности | not-evaluated | ДОПУЩЕНИЕ НЕ ПРОВЕРЕНО |
| `false` | unsupported | НЕПРИМЕНИМО |

Два решения, которые важно не переделывать:

- **НЕ добавлять под это новое сито с номером.** Номер изменил бы
  `sieve_numbers()`, и мета-сито С13 (объявленные пропуски) дало бы FAIL всем
  старым кейсам — массовый переворот вердиктов не из-за корпуса.
  Предпосылка реализована пост-вердиктным хуком в `run()`, вне `ALL_SIEVES`.
- **Хук понижает ТОЛЬКО ПОДТВЕРЖДЕНО.** Непроверенное допущение не
  делает опровержение мягче: если число не сошлось, оно не сошлось при
  любой предпосылке.

**Шидак — НЕ Бонферрони** (`goldsieve/sidak.py`, самопроверка 24). При одном
и том же семейном уровне 0,05 и M = 123 201:

| поправка | локальный p | порог, сигма |
|---|---|---|
| Шидак \(1-(1-\alpha)^{1/m}\) | 4,16338e-7 | 5,0613316768 |
| Бонферрони \(\alpha/m\) | 4,05841e-7 | 5,0661974955 |
| разность | — | +4,866e-3 |

Бонферрони строже при любом m ≥ 2 и совпадает с Шидаком точно только при
m = 1 (1,959964σ). В кейсе хранятся ОБА числа и разность — называть одно
другим запрещено.

**Устойчивая запись обязательна.** `-expm1(log1p(-alpha)/m)` даёт
относительную ошибку 6,7e-17, прямая запись `1-(1-alpha)**(1/m)` — 1,3e-10,
то есть в 2·10⁶ раз хуже. Наивная версия сохранена как `sidak_local_p_naive`:
она объект измерения, а не мёртвый код.

**Три пути, а не два.** Путь A — `inv_cdf` в double; путь B — mpmath 50 знаков
через `erfinv`; путь C — двоичный поиск по `erf`. Путь C НЕ выброшен при
появлении B: он делит арифметику с путём A, и общая потеря точности двух
путей без третьего осталась бы незаметной. `abs_err_sigma` A против B = 0,0.

**Границы и монотонность проверяются, а не предполагаются.** m ∈ {1, 2, 3, 10,
100, 20 412, 123 201, 10⁶, 10⁹}: порог растёт, локальный p падает, порядок
поправок сохраняется. Обратная сверка даёт ровно 0,05. При α = 1e-12 обе
поправки численно сходятся (8,116817e-18) — разница второго порядка по α.

**Правило для реестра.** Формулировка области охвата идёт в ОТДЕЛЬНОЕ поле
`scope_statement`, а НЕ в имя claim: имя обязано совпадать с `name=` в кейсе,
иначе регресс потеряет сопоставление. В отчёте обязательно фиксируется, было
ли допущение частью исходного рецепта. Здесь — было, но НЕЯВНО: формула
входила в отпечаток рецепта, но поля для предпосылки не было, и читатель не
имел шанса увидеть допущение.

**Сборка архива скила больше не ручная** (`build_skill.py`, самопроверка 10,
шаг гейта). Предел 100 записей достигнут, значит каждый новый файл
требует решения «что не кладём», а решение на глаз однажды выбросит
модуль инструмента. Список исключений живёт в `skill_exclude.txt`, а сборка
ОТКАЗЫВАЕТСЯ работать, если в списке путь, которого нет в источнике (список
молча перестал исключать) либо путь из `goldsieve/`, реестра или гейта.

Что осталось не доказанным после тика 48: степень зависимости испытаний
корпуса (на Ω_Λ M_eff = 2008 из 123 201 → 4,21σ; общей оценки нет, реальный
порог вероятно НИЖЕ 5,0613σ); доля ложных срабатываний хука (0 из 20 →
около 14 % по правилу трёх, нужно N ≥ 300); полнота правила
`requires_declaration`. Ничего физического тиком 48 не установлено.

Источники поправок: [Šidák 1967, JASA 62(318) 626–633](https://doi.org/10.1080/01621459.1967.10482935);
[Li & Ji 2005, Heredity 95 221–227](https://doi.org/10.1038/sj.hdy.6800717);
[Gross & Vitells 2010, EPJ C 70 525–530](https://doi.org/10.1140/epjc/s10052-010-1470-8).

## Тик 89 (2026-08-18): режим «закрытие научного долга»

Пользователь потребовал прекратить наращивание числа вердиктов: прогрессом
считается СНИЖЕНИЕ неоднозначности рецепта, а не рост реестра. Практические
правила, которые из этого вышли.

**0,4220 — это НЕ точный GUE.** Число 0,42201569295012265 = √(3π/8 − 1) есть
std приближения Вигнера; точный (Fredholm) закон GUE даёт 0,4242576222440628.
Разница 0,53 % больше, чем эффекты, о которых идёт спор, поэтому подпись
«exact GUE» на этом числе — дефект, а не стилистика. В корпусе подписи уточнены
(`gue_label_fix.py`, идемпотентно, числа не менялись), а неверная подпись
запрещена машинно: `gue_label_guard.py` (10 строковых фикстур + мутационная цель
на обходе дерева) стоит двумя шагами в `ci_gate.sh`. Regex обязан иметь границы
`(?<![\d.,])0[.,]4220\d*`, иначе ловится хвост нуля дзеты `27040.422044460`.

**Правка подписи в корпусе ломает парсеры кейсов.** Сразу после уточнения
регресс дал два `НЕ СОПОСТАВЛЕНО`. Правило: после ЛЮБОЙ правки корпуса —
перепрогон регресса, парсеры приводятся к приёму обеих подписей
(`Std vs GUE(?: Wigner surmise)?`), вердикт сохраняется, а смена отпечатка
входов получает reason-code `corpus-data-changed`. Откатывать правку корпуса
из-за упавшего парсера нельзя: это вернуло бы неверный термин.

**Недоступность чужого устройства — не срыв тика.** Машинный разбор токенов

dependency_missing / timeout / agent_error / policy_skip) показал: 40 из 47
доступных событий — это офлайн ноутбука, то есть `deferred`, а не `abort`.
Введены счётчик `deferred_device_offline` (НЕ входит в числитель доли
деградации) и очередь `replay_queue.py`: задача ставится по платформе, повтор не
дублируется, а считает попытки. Семь событий не имели примечания вовсе, поэтому

помечает событие и инкрементирует `note_missing`. Категория, которую нельзя
доказать, считается срывом — чтобы статистика отказов не занижалась.

**Вариант перебора выбирается только с машинным аргументом.** `prefilter.decide`
теперь поднимает `VariantChoiceError` при отсутствии имени варианта или причины
короче 12 символов, а паспорт решения ВСЕГДА печатает ОБА размера
(`standard = 20412`, `actual = 123201`), выбранный вариант и причину; ложный
паспорт (диапазоны против имени) отвергается. Это кодовая защита от ошибки
лупа 7, где неоднородная пара дала верный знак и неверную величину.

**Текстовое «OPEN» заменяется протоколом.** `bblm_spec.yaml` +
`bblm_protocol.py`: восемь обязательных элементов, у каждого предикат наличия И
проверка содержимого, поэтому `present: true` без полей отвергается. Вердикт
выносит код: ВОПРОС при любом отсутствующем элементе, с точным перечнем
недостающего в JSON. Мутация каждого элемента ловится (8/8).

## Временная недоступность — не отказ по существу (тик 97)

Доклад тика писал «macOS повтор возвращён в очередь», а код ставил `failed`
навсегда: `complete` знал только `ok|fail`. Задача выпадала из очереди, повтор
становился невозможен, и расхождение доклада с файлом никто не ловил. Правило:
у очереди обязаны быть ТРИ исхода — `ok -> done`, `deferred -> queued`
(attempts+1, `claimed_at` снимается), `fail -> failed`; временная причина
(`device_offline`, таймаут runner) закрывается только через `deferred`.

Второй дефект вскрылся при лечении первого: дедупликация `enqueue` смотрела
только на `queued|claimed`, поэтому задача, побывавшая в `failed`, получала
ВТОРУЮ запись с тем же id, и после возврата в очередь `claim` взял бы одну
работу дважды. Дедупликация обязана быть по id в ЛЮБОМ состоянии.

Общий вывод: **у любого файла состояния должен быть машинный аудит
согласованности, стоящий шагом гейта** — `replay_queue.py audit` даёт код 1 при
временной причине в `failed` и при дубле по id. Обе ветви аудита обязаны иметь
измеренную чувствительность, и проверка «отказ по существу потерей не считается»
проверяется АДРЕСНО по id, а не по коду возврата аудита: иначе она проходит за
счёт другой, уже потерянной задачи, то есть тавтологично.

## Роль файла — по КОРНЮ каталога, а не по имени (тик 171)

Гейт закрывался на собственных докладах три десятка раз. Причина не в тексте
проверки, а в её устройстве: роль файла опознавалась СПИСКОМ ИМЁН и glob-шаблонов
(`AUDIT_LOG_NAMES`, `AUDIT_LOG_GLOBS`), а каждый тик рождал новое имя
(`tickNNN-gate.txt`, `tickNNN-summary.txt`, `state-tickNNN.md`). Каждый ремонт
дописывал ещё один шаблон, следующий тик придумывал имя вне шаблона.

**Гонка шаблона с генератором имён не выигрывается.** Роль определяется КОРНЕМ:
всё внутри `cron_tracking/` — журнал прогонов по построению, поэтому ЛЮБОЕ
ранее неизвестное имя там автоматически имеет роль `audit_log`; корень корпуса
остаётся сильнее имени. Регресс обязателен на ИСТОРИЧЕСКИХ ложных
срабатываниях (имена из писем закрытых гейтов) плюс на двух заведомо новых
именах, не покрытых ни одним шаблоном — иначе тест доказывает лишь то, что
шаблоны перечислены.

## Ротация журнала выглядит как деградация аудита (тик 171)

Охват машинного разбора токенов срыва падал с 47 до 3 из 52, и это читалось как

с `identity_holds` и кодом причины неустранимости. Утрата, объявленная кодом, —
это честный результат; молчаливое «разобрано 3» — нет.

## Вторая платформа находит то, что первая не может (тик 171)

Допущение «локального устройства нет, значит межплатформенная проверка
невозможна» было ЛОЖНЫМ: размещённые исполнители GitHub для публичного
репозитория доступны, Actions включены, рабочие процессы уже шли на разрешённой
ветке. 28 тихих `deferred_device_offline` — цена непроверенного допущения.
Прежде чем объявлять ограничение инфраструктуры постоянным, ограничение
проверяется кодом.

Четыре прогона нашли ТРИ класса дефекта, невидимых на Linux, потому что там
локальная кодировка utf-8:
1. поток вывода в cp1252 роняет русский вывод до первой проверки
   (`UnicodeEncodeError`) — лечится `reconfigure(encoding="utf-8")` в
   `__init__.py` пакета, один раз для всего;
2. чтение подпроцесса в локальной кодировке (`UnicodeDecodeError` в потоке
   читателя, дальше `stdout=None` и `TypeError`), плюс литерал `"python3"`,
   которого на Windows нет — `sys.executable` и `encoding=` обязательны;
3. запись файлов без явного `encoding=` — на Windows падает на первом же
   русском символе.

Отдельные места не правятся поштучно: класс закрывается ЛИНТЕРОМ
(`portability_lint.py`) с режимом `--fix`, шагом гейта и мутационной целью.
Исключение `os.open` (низкоуровневый дескриптор, `encoding` не принимает)
зафиксировано фикстурой: первая версия линтера пометила его и сломала блокировку
журнала — **машинная правка обязана проверяться `ast.parse` и самопроверками
затронутых модулей, иначе линтер становится источником дефекта.**

Область прогона не подменяет область гейта: `ci_gate.sh` требует корпуса,
которого в репозитории нет, поэтому задачи полного каскада остаются `queued`, а
закрывается ровно та задача, что описывает самопроверку пакета.

## Отсутствующий элемент протокола: код или машинный ВОПРОС (тик 171)

Пять элементов протокола BBLM закрывались так: четыре — кодом с результатом,
пятый — ВОПРОСОМ с кодом причины `analytic_source_absent` и полем
`what_would_close_it`. Текстовое «OPEN» запрещено: оно не проверяется и не
устаревает.

Рабочие приёмы этих элементов:
- **погрешность прежде сигм**: без бутстрэпа (400 повторов, фиксированный seed)
  у отклонения нет знаменателя, и «расхождение в процентах» неинтерпретируемо;
- **масштаб против формы**: наилучший ЧИСТЫЙ масштаб — среднее геометрическое
  отношений `obs/ref` по статистикам; если остаток после него многократно
  превышает бутстрэп-сигму (здесь p50 = +14,8σ при α = 0,976057), масштабом
  картина не объясняется;
- **вне выборки**: коэффициент обучается на нижнем диапазоне высот
  (L = 7,898) и проверяется на верхнем (L = 9,113). Обученный c = −0,2014 даёт
  +0,13σ, цитатный c = +1,4720 даёт +61,8σ — знак цитаты ПРОТИВОПОЛОЖЕН
  наблюдаемому направлению. Согласие внутри одного набора нулей от подгонки
  неотличимо;
- **тавтология разводится стеком**: развёртка — чистый Python с своим парсером,
  эталон — модуль Фредгольма, θ — scipy `loggamma`.

Новый claim при этом НЕ создаётся, если направление уже покрыто
зарегистрированным вердиктом (`zeta:bblm:finite_height_comparison:v1`):
арифметический повтор закрытого случая прогрессом не является.

## Два источника истины — механизм холостого тика (тик 205)

Тридцать три тика подряд (172–204) выдавали идентичный доклад и наращивали
счётчик отложений с 28 до 54. Ни одна проверка не падала: инструмент был
исправен, а работа стояла. Разбор писем дал две машинные причины.

**Первая: у учёта оказалось ДВА источника истины.** Доклады читали рукописную
`bblm_spec.yaml`, а расчёт закрывал элементы в `bblm_elements.json`. Расчёт не
обязан править спецификацию, поэтому «3 из 8» жило рядом с фактическими
«7 из 8» и воспроизводилось каждым тиком. Правило: **у каждого числа в докладе
один машинный источник**; производный файл заполняется ИЗ первичного кодом
(`--sync` переносит СОДЕРЖИМОЕ, а не признак `present: true`), а расхождение
двух артефактов даёт код 1 и стоит шагом гейта. Проверка расхождения обязана
быть ПОИМЁННОЙ: сравнение количеств историческую рассинхронизацию не ловит, и
это доказывается отдельной проверкой в самопроверке.

**Вторая: способ работы, обречённый на откладывание.** ОС-матрица запрашивалась
у локального устройства, недоступного 33 тика, при живом облачном исполнителе.
Счётчик отложений создавал видимость учёта и тем скрывал, что метод выбран
неверно. Правило: **если счётчик отложений растёт монотонно три тика подряд,
неверен метод, а не обстоятельства** — метод меняется, счётчик закрывается
навсегда.

Два машинных предохранителя, поставленных в задание крона: sha256 текста
доклада в `last-report-digest.txt` (совпадение с предыдущим = провал тика,
обязан найти причину застоя) и обязательная ревизия молчащих проверок после
трёх тиков без изменений файлов инструмента — грепом по шагам гейта, которые
всегда PASS и ни разу не падали. **Шаг гейта, который никогда не падал, не
доказан как чувствительный.**

Общий вывод для аудита самого себя: одинаковый доклад — не стабильность, а
диагноз. Проверять надо не только корпус, но и ПОТОК СВОЕЙ РАБОТЫ: письма
предыдущих тиков — такие же входные данные, как файлы корпуса.
