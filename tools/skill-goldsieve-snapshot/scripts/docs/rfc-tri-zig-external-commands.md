# RFC: механизм внешних команд для `tri` на Zig

Статус: **черновик, работы не начаты.** Документ подготовлен по пункту 7
приказа тика 43. Требуется отдельное разрешение на PR; до него в
`gHashTag/trinity` не вносится ни строки.

Дата: 2026-08-15. Автор черновика: агент аудита (тик 43).

## 1. Зачем

В репозитории `trinity` есть свой `tri` на Zig (`src/tri/main.zig`,
`src/tri/tri_plugin.zig`). Команды аудита живут отдельно — оболочкой на Python
в песочнице (`/home/user/workspace/goldsieve/tri`). Пользователь набирает
`tri` в двух разных смыслах, и это уже источник ошибок.

Что НЕ доказано и не заявляется: что перенос ускорит работу. Тик 43 измерил
машинное время оболочки (см. `loop16/bench.json`); оболочка не ускоряет
работу, а добавляет накладной расход. Смысл переноса — единая точка входа и
одно имя команды, а не скорость.

## 2. Область

В области: механизм, которым Zig-`tri` вызывает ВНЕШНЮЮ команду (в том числе
Python-скрипт аудита), передаёт аргументы, возвращает код и оставляет запись в
журнале вызовов.

Вне области: перенос самого каскада сит на Zig. Каскад опирается на numpy,
scipy и mpmath; переписывание арифметики на другом языке означает новую
реализацию эталонов, то есть новый источник расхождений. Пока такой переход не
обоснован отдельным измерением, он не рассматривается.

## 3. API внешних команд

Предлагается объявление внешних команд файлом-манифестом, а не жёсткой
таблицей в коде: иначе каждое новое сито требует правки Zig и сборки.

```
# tri-external.toml
[[command]]
name        = "audit-gate"       # имя, видимое в `tri --help`
exec        = "python3"          # исполняемый файл
args        = ["ci_gate.sh"]     # неизменяемая часть аргументов
cwd         = "tools/goldsieve"  # ОТНОСИТЕЛЬНО корня репозитория
pass_args   = false              # передавать ли пользовательские аргументы
timeout_sec = 1800
locked      = true               # брать исключительный замок
artifacts   = ["baseline/manifest.json"]
```

Правила:

1. `exec` разрешается только из списка, объявленного в манифесте, и ищется в
   `PATH`; строка от пользователя исполняемым файлом стать не может.
2. `cwd` обязан лежать внутри корня репозитория; путь нормализуется и
   проверяется на выход за корень (`..`, симлинк на внешний каталог) до
   запуска.
3. При `pass_args = false` пользовательские аргументы отбрасываются с
   сообщением, а не молча.
4. Оболочка не запускается: вызов через `execve` без shell. Никакой строки,
   собираемой конкатенацией.
5. Среда наследуется минимально: `PATH`, `HOME`, `LANG` и явно объявленные
   `env` из манифеста. Всё остальное вычищается — иначе поведение зависит от
   того, из какого терминала запущено.

## 4. Модель безопасности

Угроза, которую механизм создаёт: `tri` превращается в средство запуска
произвольного кода из файла в репозитории. Значит манифест — часть доверенной
базы.

- Манифест читается ТОЛЬКО из корня репозитория, не из текущего каталога и не
  из домашнего: иначе подложенный файл в чужом каталоге перехватывает команды.
- Изменение манифеста обязано попадать в обзор кода как изменение
  исполняемого кода, а не конфигурации. Предлагается CODEOWNERS на
  `tri-external.toml`.
- Sha256 манифеста печатается в журнале вызовов при каждом запуске внешней
  команды. Незаметная правка становится видимой в истории.
- Записи журнала — append-only JSONL; для защиты от незаметной правки
  предлагается хеш-цепочка (каждая запись содержит sha256 предыдущей). Это же
  замечание пользователь высказал по журналам аудита; здесь оно применяется к
  журналу оболочки.
- Внешняя команда не получает повышенных прав, `setuid` не используется.
- Запрет на сеть не декларируется (Zig этого не обеспечит), а фиксируется как
  НЕ покрытое механизмом: ответственность на самой команде.

## 5. Коды выхода

Единая таблица, чтобы CI мог различать «проверка нашла проблему» и «механизм
сломался»:

| код | смысл |
|---|---|
| 0 | команда прошла |
| 1 | проверка не прошла (содержательный отказ) |
| 2 | ошибка употребления: неизвестная команда, плохие аргументы |
| 3 | замок занят: другой тик выполняется |
| 4 | манифест внешних команд не найден или не разобран |
| 5 | нарушение безопасности: `exec` вне списка, `cwd` вне корня |
| 124 | превышен `timeout_sec` (совместимо с `timeout(1)`) |
| 128+N | команда убита сигналом N |

Коды 124, 130, 137, 143 трактуются как `aborted`, не `failed` — как уже
сделано в Python-журнале (`goldsieve/runlog.py`). Смешивать срыв с провалом
нельзя: срыв инфраструктуры и найденная ошибка требуют разных действий.

## 6. Переносимость

- Linux и macOS: `posix_spawn`, ожидание через `waitpid`.
- Windows: `CreateProcessW`; замок через файл с `FILE_SHARE_DELETE` вместо
  `flock`; сигналов нет, поэтому 128+N не применимо и обязано отображаться в
  отдельный код.
- Статус платформ до измерения — `not-evaluated`. Формулировка результата:
  «проверено на указанных версиях», не «платформонезависимо».
- Требуется матрица сборки в CI прежде, чем механизм объявляется рабочим на
  платформе.

## 7. План отката

1. Механизм закрыт флагом сборки `-Dexternal-commands=false` (по умолчанию
   выключен на первом этапе).
2. Первый PR добавляет только чтение манифеста и `tri external list` — без
   запуска. Обзор видит поверхность атаки прежде, чем появится исполнение.
3. Второй PR добавляет запуск за флагом. Откат = сборка с флагом `false`.
4. Третий PR включает флаг по умолчанию — только после матрицы платформ и
   после того, как хеш-цепочка журнала прошла собственные тесты.
5. Полный откат: удаление `tri-external.toml` не ломает сборку; при
   отсутствии манифеста `tri` работает как сейчас (код 4 только для команды
   `external`).

## 8. Критерии приёмки

- Интеграционные тесты по аналогии с `tri_integration_test.py`: фон, замок,
  падение дочернего процесса, таймаут, неполный журнал.
- Подставка: попытка вызвать `exec` вне списка обязана давать код 5, и тест
  обязан падать, если проверка снята.
- Двойной запуск исключительной команды даёт код 3, а не ожидание.
- Sha256 манифеста присутствует в каждой записи журнала.
